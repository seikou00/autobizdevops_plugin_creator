# AutoBiz 看板插件引导技能使用手册

草稿 · 适用于引导技能 1.3.2

用这个技能可以从业务想法搭建 DevClaw 看板插件、把现成技能组装成流程，或给已有插件增删改节点。默认由模型起草配置和技能，你确认流程、产物和运行方式。熟悉配置的用户也可以选择自行填写。

## 开始使用

1. 解压 `booter-public.zip`，把完整的 `booter/` 目录加载到支持技能的 Agent 中。技能入口是 `booter/SKILL.md`，同目录下的脚手架和模板会在生成插件时用到。
2. 确认 Agent 可以访问你的工作目录并运行 Python 3.9 或以上版本。
3. 在新对话中调用 `autobiz-plugin-skeleton`，也可以直接描述要做的事。

`booter-public.zip` 用于加载引导技能。引导结束后生成的插件 ZIP 才用于导入 DevClaw。

## 选择起点

启动技能时，如果还没有给出具体任务，入口会提供以下三项。

| 起点 | 适用情况 | 可以这样说 |
| --- | --- | --- |
| 从想法搭建 | 有业务需求，希望梳理成一套流程 | “帮我做一个文档起草和评审插件。” |
| 用现成技能组装 | 有技能目录，希望复用部分或全部技能 | “读取 `./my-skills`，建议怎样把这些技能组装成插件。” |
| 修改已有插件 | 有插件源目录，希望增删改节点 | “在 `./my-plugin` 的开发节点后面加一个测试节点。” |

如果已经给出了具体任务，模型会直接进入对应流程。界面无法展示完整选择题时，可以在对话里回复选项名称。

推荐选择 **模型起草，我来确认**。每轮通常只讨论一个主要决定，已经提供的信息会继续沿用。可以说“给我一个例子”“先标为待定”或“回到上一项，我想调整”。选择 **我自己填写配置** 时，模型会提供骨架或字段说明，等你填好后再检查。

## 从想法搭建

1. **说清用途。** 先描述要完成的工作，例如“把需求整理成一份文档，再由另一个步骤检查遗漏”。还没有完整想法时，可以先说最想减少哪项重复工作。
2. **确认流程。** 模型会提出简短的步骤，例如“起草文档 → 评审文档”。先确认这些步骤符合实际工作，再逐个细化。
3. **逐个确认节点。** 说明每一步做什么、是否需要保存文件、什么情况下算完成。例如起草节点把初稿保存为 `DRAFT.md`，评审节点读取初稿并记录结论。列为必需的文件如果缺失或为空，节点将无法完成。诸如“覆盖所有验收条件”这样的质量要求应写进技能的工作说明。
4. **确认附加能力和保存目录。** 需要把项目规范带入会话或同步产物时，模型会继续询问相关设置。新建目标目录应当为空或尚未创建。
5. **审阅摘要。** 查看名称、目录、节点顺序、产物、模块和技能来源。缺少的节点技能可以请模型逐个起草，也可以自行编写。

每个项目默认在 `.autobizdevops/` 保存进度、产物和日志。你可以在新插件首次使用前请模型设置其他目录名，尤其是同一个项目会使用多个插件时。配置位置和已有数据的迁移方式见[自定义目录名](plugin-customization.md#自定义-autobizdevops-目录名)。

## 用现成技能组装

1. 提供技能目录。有流程配置、共享资料或独立的 `agents/` 目录时，一并说明位置。
2. 查看模型的盘点结果。它会建议哪些技能成为看板节点、哪些作为辅助能力，以及怎样排序。重点确认职责重叠、执行顺序和必需产物。
3. 确认导入范围。选择哪些技能成为节点和选择哪些文件进入插件是两件事。整批导入会复制技能集合，包含辅助技能及集合内的共享资源。如果只想导入部分文件，请在确认前明确说明范围，模型会先核对依赖。
4. 审阅导入和补齐方案。模型会指出缺失的脚本、模板或子代理文件，以及需要适配的旧引用。缺少节点技能时，可以请模型根据已确认的职责和完成条件起草。

## 修改已有插件

提供包含 `plugin.scaffold.json`、`workflow.json` 和相关技能的源目录，并说明想改的节点。如果手头只有安装包，请先说明。模型会寻找源配置，并解释现有文件能提供哪些信息。

| 操作 | 你需要确认什么 |
| --- | --- |
| 新增 | 插入位置、职责、使用哪个技能、是否要产生文件 |
| 删除 | 原职责是否仍需完成，以及下游是否继续使用原产物 |
| 修改 | 调整显示名称、职责、产物、技能绑定或执行位置 |

例如，可以说“在开发后、评审前加一个测试节点，生成 `TEST_REPORT.md`”。模型会展示修改前后的流程，并检查评审技能是否需要读取测试报告。只改显示名称时，节点标识通常保留。已发布的插件如果有进行中的任务，请把这个情况告诉模型，便于核对状态兼容性。

确认具体差异后，模型会修改源文件、重新生成并检查。需要新安装包时，明确说“检查通过后帮我打包”。

## 自定义 Agent 运行模式

出现“你希望怎样设置节点的 Agent 运行模式？”时，可以选 **沿用默认（推荐）** 或 **自定义运行模式**。新插件默认使用多 Agent。

选择自定义后，先决定是更改全局默认、只调整指定节点，还是两者都改。节点没有单独设置时会继承全局默认。

| 模式 | 配置值 |
| --- | --- |
| 多 Agent | `multi` |
| 单 Agent | `solo` |
| Agent 团队 | `agent_team` |
| 工作流 | `workflow` |

可以直接说“全局用多 Agent，只有编码节点用 Agent 团队”，或“把全局默认改成单 Agent”。模型会把设置列入确认摘要，随后写入 `modules/session.json`。如果界面没有显示自定义选项，可以直接在对话里说出要设置的模式或节点。

## 确认、检查与打包

确认前核对流程顺序、必需产物、技能来源和运行模式。修改已有插件时，重点看前后差异、受影响的技能和待解决的兼容性问题。可以用“第二步改成……”指明需要调整的地方。

确认后，模型会检查源配置，补齐或导入技能，再重新生成看板和运行文件。检查结果会指出有问题的文件和位置。需要交付安装包时，打包成功后可以在插件目录的 `dist/` 下找到 ZIP，随后将它导入 DevClaw。每次打包会自动递增补丁版本号。

| 检查提示 | 怎么处理 |
| --- | --- |
| `TODO_FIELD` 或 `TODO_PLACEHOLDER` | 补齐未填写的配置或技能内容，再检查。 |
| `SKILL_MISSING` | 检查节点绑定的技能名与技能目录名是否一致，或补齐缺少的技能。 |
| `SKILL_REF_DANGLING` | 确认引用的模板、资料或脚本是否已导入，以及路径是否正确。 |
| `LEGACY_ENTRY_REF` | 请模型定位技能里的旧状态命令，确认处理方案后更新。 |
| `BUILD_STALE` | 源配置或技能已变化，请模型重新生成后再打包。 |
