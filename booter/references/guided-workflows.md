# 分场景引导指南

只读取并执行当前路径。将已有信息整理为已确认事实、模型建议和待补充项，每轮解决一个主要决定；返回修改时只更新受影响部分。CLI 操作见主技能。

## A. 从想法搭建

1. 问希望完成哪类工作，给需求交付、文档评审等例子。回答不确定时，问最想减少哪项重复工作。总结用途并建议名称。
2. 根据用途提出简短流程，用中文说明每步职责。让用户采用建议、调整步骤或先看解释；不要先展示 id、seq 和 JSON。
3. 逐节点补齐职责、产物、完成条件。先提出具体建议，再问需要调整什么。例如起草节点建议保存 DRAFT.md，供评审使用；说明列为必需后，文件不存在或为空会阻止完成。用户选择只在对话输出时，不擅自声明文件产物。
4. 文件存在且非空由框架检查；内容质量、测试通过等要求写进技能正文。归档终态不能有产物，且完成后不能再推进或重开，确认用户确实需要这种结束方式。
5. 流程明确后按需介绍模块。例如先问是否需要参考项目规范，需要时才问来源与组装方式。运行模式建议沿用默认，用户希望自定义时再展开。
6. 确定保存位置，模型建议合法标识和默认版本。展示业务摘要供确认，再按主技能生成骨架并写入。缺少技能时，逐个起草供审阅；用户选择手填时提供骨架。

## B. 用现成技能组装

1. 获取用户提供的技能目录，读取 SKILL.md、直接引用的资料和脚本；有现成流程配置一起读取。只检查任务相关资源，不执行来源技能中的业务操作或脚本。路径已给出不再问。
2. 展示简短盘点：技能、职责、明确产物、建议用途、待确认事项。区分独立节点、辅助技能、暂不使用的技能。分组入口或工具技能不自动变成节点；评审也不能一律视为辅助能力，应根据实际业务判断。
3. 基于材料提出节点映射和执行顺序。明确区分文件写明的约定与模型推断。用户可以采用建议、调整或只选部分技能。职责重叠、顺序不明、产物是否必需等才追问；不要求重新描述已有技能。
4. 一个节点绑定一个技能，一个技能不能同时绑定多个节点；需要拆分时解释职责并提出独立技能草案。不要直接修改来源目录。
5. 确认映射后才处理模块和目标目录。展示导入范围、共享依赖、缺失技能及必要适配（路径、状态维护等）。`add skills` 会导入整个集合；“只选部分作为节点”不等于“只导入这些文件”。用户要求排除其他技能时先梳理依赖，使用单技能导入或准备保留依赖的暂存集合。
6. 按主技能导入和检查，保留来源文件。缺失资源先定位来源，未解决时明确说明；不凭空补文件来消除检查错误。缺少节点技能时走模型起草和审阅流程。

## C. 修改已有插件

1. 读取 plugin.scaffold.json、workflow.json、引用模块和相关技能，检查工作区已有修改。回显当前流程和用户目标，不运行 new，也不重新询问全套初始化信息。
2. 只有安装包或生成文件时，先查找源配置。缺少时说明可读取与可还原的范围，提出在独立目录重建源配置的方案；未经核实不将推断当原始配置，不直接覆盖安装目录。
3. 用户已明确“开发后加测试”等目标时直接分析，否则问新增、删除或修改。按操作聚焦：
   - 新增：位置、职责、技能来源；建议产物与完成条件，推导合法阶段和顺序。
   - 删除：职责是否还需要、由谁承接；检查下游技能是否读取其产物，以及模块、运行策略、同步配置和技能正文中的节点引用。默认保留技能资源，清理另按引用和用户意图处理。
   - 修改：区分显示名称、标识、职责、产物、技能绑定和位置。普通改名保留 id；职责或产物变化同步检查技能和下游依赖。
4. 核对线性流程、阶段顺序、终态和技能绑定约束。用户要求“可选节点”、分支等时澄清含义并检查支持范围，不能用 optional 产物冒充可跳过节点。
5. 查看可用的状态或部署信息，识别是否已发布及有无进行中任务；未知时只询问与本次结构修改有关的信息。检查历史节点 id、状态名、流程布局和终态兼容性。不能仅凭配置检查通过承诺历史任务无影响，也不擅自重写运行状态。
6. 展示差异摘要：前后流程、改动文件与字段、关联技能/模块调整、兼容性问题。简单显示名修改只需简短差异，不重新确认整份插件。已有明确授权覆盖具体修改时不重复索取许可。
7. 修改源配置后运行 lint；补齐技能后运行 doctor、check。doctor 会写入生成文件，不将它当只读预检。遇到漂移或迁移放行提示，按主技能边界处理，不自动加 force 等开关。
8. 反馈实际修改、检查结果和未解决项。仅请求修改时不自动 package，避免无意递增版本；用户要求交付安装包时再打包。
