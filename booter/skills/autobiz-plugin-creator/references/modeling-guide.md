# 建模指南：把业务流程拆成阶段、节点和产物

看板插件的流程只有一个概念：**节点**。每个节点由一个技能负责，在 Feature 目录中产出自己的产物。节点按 `seq` 从小到大线性推进，并按 biz、dev、ops 三个阶段分组显示在看板上。

## 拆分原则

- **一个节点 = 一个能独立交付的步骤**：它有明确的“做完了”的标志，通常就是一份产物。拆得太细，看板上全是琐碎状态；拆得太粗，一个技能要做太多事；
- **一个节点只绑定一个技能**：技能的 `SKILL.md` 开头写着本节点的状态命令，两个节点不能共用一个技能；
- **阶段只用来分组**：需求、方案放 `biz`，设计、计划、编码放 `dev`，发布、归档放 `ops`。`seq` 必须按 biz → dev → ops 递增；
- **`seq` 可以跳号**：写 `10、20、30`，以后在中间插节点时不用改其他节点；
- **最后一步是归档时用终态节点**：`terminal: true`，没有输出，完成后 Feature 进入 `archived`，不能再推进或重开。

## 产物

- 写文件名，路径相对 Feature 目录，可以含 glob（`specs/**/*.md`）；
- 输出默认是必需的：推进到完成时，框架检查每一项至少匹配一个文件，且文件去掉首尾空白后不为空；可有可无的写成 `{"path": "PR_BODY.md", "optional": true}`；
- 后面的节点可以再次输出同一个路径（例如在后续阶段更新），以第一个输出它的节点为生产者；
- 节点要读哪些上游产物写在技能正文中，不写进配置；
- 产物 id 由路径推导，`PLAN.md` 和 `plan.md` 会推导出同一个 id，要换文件名；
- 不能用 `state.json`、`hooks.ndjson`、`sync-status.json`、`ARTIFACT_CATALOG.json` 作产物名。

## 完成条件写在哪里

框架只做最小检查：必需产物存在且非空。内容是否合格、代码是否提交、测试是否通过，都写进技能正文，作为执行完成命令的前提：

> 完成前先确认：评审结论写在 REVIEW.md 的“结论”一节；有阻断项时不要执行完成命令，先回到起草节点。

编码节点通常不写 `outputs`：代码不作为产物，“代码已提交、测试通过后再执行完成命令”写在技能正文中。

## 正反例

| 写法 | 问题 | 改成 |
|---|---|---|
| 节点 `dev.plan` | id 不加阶段前缀 | `plan` |
| 两个节点都绑定 `doc-writer` | 一个技能只能绑定一个节点 | `doc-draft`、`doc-review` |
| `biz` 节点 `seq: 5`，`dev` 节点 `seq: 3` | `seq` 要按阶段递增 | `dev` 节点改为 `seq: 6` |
| 输出 `PLAN.md` 和 `specs/plan.md` | 两个路径推导出同一个产物 id `plan` | `specs/plan.md` 改为 `specs/task-plan.md` |
| 评审节点没有输出，靠模型自觉 | 看板上无从判断是否做完 | 输出 `REVIEW.md`，结论要求写在技能正文 |
| 归档节点写了 `outputs` | 终态节点不能有输出 | 去掉 `outputs`，归档动作写在技能正文 |

## 建模表格

和用户确认流程时，按这张表回显，用户确认后才写入配置：

| seq | 阶段 | 节点 id | 显示名 | 技能 | 输出产物 |
|---|---|---|---|---|---|
| 10 | biz | `draft` | 起草 | `doc-draft` | `DRAFT.md` |
| 20 | biz | `review` | 评审 | `doc-review` | `REVIEW.md` |
| 30 | ops | `archive` | 归档 | `doc-archive` | —（终态节点） |
